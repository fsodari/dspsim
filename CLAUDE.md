# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

dspsim is a C++23 discrete-event (delta-cycle) simulation engine for hardware designs, exposed to Python (>=3.14) via nanobind as `dspsim._framework`. Models are either hand-written C++/Python modules or Verilator-generated models of SystemVerilog RTL, or of synthesizable VHDL that GHDL turns into Verilog first. Built with scikit-build-core + CMake, managed with `uv`.

## Commands

```bash
# Editable install of the Python package (rebuilds the C++ extension on import when sources change)
uv sync -v

# Python tests
uv run pytest tests
uv run pytest tests/test_signal.py::test_name

# C++ tests (Catch2, single `tests` executable). First run needs --configure.
uv run scripts/cpptest.py --configure          # configure + build + run, Release, build dir ./build
uv run scripts/cpptest.py                      # rebuild + run
uv run scripts/cpptest.py "[dff]"              # extra args are passed to the Catch2 binary (tag/name filter)
uv run scripts/cpptest.py --no-build "[coro]"  # run without rebuilding

# C++ benchmarks against SystemC (docs/Benchmarks.md). First run needs --configure.
uv run scripts/benchmarks.py --configure       # configure + build + run every case, report dspsim/SystemC
uv run scripts/benchmarks.py chain/dff         # rebuild + run the cases matching a regular expression
uv run scripts/benchmarks.py --check           # only check that the engines agree on every case (seconds)
uv run scripts/benchmarks.py --save base.json  # then, after a change: --compare base.json

# VHDL tests need GHDL (5 or 6): on the path, or
DSPSIM_GHDL=/path/to/bin/ghdl uv run pytest tests/test_vhdl.py

# Lint / format Python
uv run ruff check . && uv run ruff format .
```

- `cpptest.py` passes `CMAKE_PREFIX_PATH` = the venv site-packages so CMake finds nanobind and verilator (from the `verilator-dspsim` wheel). Run it via the venv.
- On first configure, if `.deps/install` is missing, CMake runs `scripts/install_deps.sh` (or `install_dev_deps.sh` with `-DINSTALL_DEV_DEPS=ON`) to build spdlog / Catch2 / SystemC locally. FST tracing needs the lz4 development files (`liblz4-dev` / `lz4-devel` on Linux, `brew install lz4` on macOS); `dspsim_target_fst_deps()` in `cmake/dspsim-utils.cmake` checks for them at configure time and adds non-default search paths (Homebrew) to a verilated target.
- ccache is optional and needs no setup: Verilator's `verilate()` looks for `ccache` and, if it is installed, uses it as the compiler launcher for the whole CMake project it is called in (the C++ tests and benchmarks here, and every JIT model build). Nothing depends on it. It does not help `uv sync` rebuilds of the package: uv builds in an isolated environment whose paths change every time, so nearly every compile is a cache miss.
- **Windows (MSVC)**: the C++ tests and benchmarks build and run with MSVC, but the wheel CI only builds `_framework` and runs pytest, so build them locally after changes to the core, the tests or the benchmarks (from a Visual Studio developer prompt, with Ninja). Two things in the environment break the build: a `VERILATOR_ROOT` environment variable pointing at another Verilator (Verilator's CMake config prefers it over the `verilator-dspsim` wheel in the venv; older Verilators generate array ports that `vport.h` does not handle), and a SystemC library built for another C++ standard than C++23 (unresolved `sc_api_version_..._cxx...` at link time; `scripts/install_dev_deps.ps1` builds it correctly).
- Benchmarks (`benchmarks/`, `docs/Benchmarks.md`) compare dspsim with SystemC on the same designs, like for like: a method process against an `SC_METHOD`, a coroutine against an `SC_THREAD`. Each suite is one `EXCLUDE_FROM_ALL` executable (`chain`, `wide`, `stream`, `events`, `sensitivity`, `timing`, `tasks`) whose cases are a design (`group`) in several process kinds (`method`, `method_dynamic`, `coro`, `coro_dynamic`); one run measures one engine of one case in a fresh process (`build/benchmarks/chain --case dff/n=500/coro --engine dspsim`), and `scripts/benchmarks.py` runs, repeats, checks and reports them. The harness (`benchmarks/harness/`) counts user-mode cycles and instructions with `perf_event_open` over the measured iterations only: construction, elaboration, the settling at time 0 (`run(0)` / the first `sc_start`) and a warm-up are excluded. All engines and kinds of a design must give the same checksum, and the driver fails if they do not. Models live in `benchmarks/models/` (`name.h` for dspsim, `name_sc.h` for SystemC; the dspsim ones do not include SystemC). A new case is a few lines in a suite's `sc_main`; a new suite also needs `add_benchmark(name)` in `benchmarks/CMakeLists.txt`. The chains (`models/chain.h`) take their length as a constructor argument and construct their levels back to back in one block of memory (`LevelStorage`). Keep both properties: a template that nests itself N times does not compile with MSVC at 500 levels (C1202) and takes GCC minutes, and allocating each level separately makes the SystemC side 13-18% slower, which changes what the benchmarks compare. The benchmarks do not use spdlog: a program must not link the compiled spdlog library together with `dspsim-core`, which contains spdlog's header-only code (duplicate symbols with MSVC, silently mixed definitions elsewhere).
- `scripts/cocotb_benchmark.py` compares dspsim against cocotb (dev dependency): `hdl/Skid.sv` is verilated for both and driven by equivalent Python testbenches next to it in `scripts/` (`cocotb_bench_dspsim.py`, `cocotb_bench_cocotb.py`, shared stimulus in `cocotb_bench_common.py`). Scenarios `clock`, `edge`, `axis`; `--scenario`, `--sim`, `--size`, `--repeat` select what runs. Both testbenches must simulate the same number of clock cycles, and the script fails if they don't.
- Wheels: `uvx cibuildwheel` (CI in `.github/workflows/build_wheels.yml`, publishes to PyPI on `v*` tags).

## Architecture

### C++ core (`src/*.cpp`, headers in `src/include/dspsim/`) → static lib `dspsim-core`
- **`Context`** owns a simulation: registered models, the eval/update delta-cycle stacks, and a time-ordered event queue. A global `ContextFactory` tracks the active context; models self-register with it on construction. `elaborate()` finalizes all models (resolving lazy port binds), locks the design, and releases the context from the global factory so a new independent context can be built. `Context::create()` takes a construction lock in `ContextFactory`: other threads block until the context is elaborated or `release()`d, and the same thread gets `ContextConstructionError` (`Context::reset()` discards it). `Context::obtain()` never creates a context; it throws unless the calling thread has one under construction, so models built outside `create()`…`elaborate()` fail. Registering a process pushes it onto the eval stack (`Context::add_process`), so it is evaluated once in the next delta cycle whenever it is registered: before the first `run()`, between runs, or from a running process (`initialize(false)` takes it off the stack again). `run(t)` settles the design (the private `eval()` runs delta cycles until nothing is scheduled; `run(0)` does only that) and advances simulated time by jumping event-to-event. `clear()` also empties the scheduling stacks.
- **Two-phase delta cycle**: `eval()` computes; `Signal::write()` only sets the pending value `d_`. `update()` commits `d_ → q_` and notifies subscribers (Changed/Posedge/Negedge), which schedules more work. All evals in a round see a consistent snapshot. An event that user code raises with `SensitivityEvent::notify()` (from a process or between runs) occurs when the evaluation phase is over, like SystemC's `notify(SC_ZERO_TIME)`: every process subscribed by then is evaluated in the next delta cycle, including one that started waiting after the call. The eval phase pops processes off the stack (last scheduled first), so the order of evaluation within a round must not matter.
- **`Signal<T>`**, **`Input<T>`/`Output<T>`** ports (bind to a signal, or hierarchically to another port; port-to-port binds are recorded and resolved recursively at `finalize()`, so bind order doesn't matter), **`Clock`** (self-rescheduling signal).
- **`PortStruct`** / **`SignalStruct`** (`struct.h`): a group of ports, or of signals, with named fields: the struct (record) port of a module and what it binds to. A field is a port or signal, an array of them, or a nested struct. `PortStruct::bind()` binds all fields by name to a `SignalStruct` (or to the `PortStruct` of a parent module) after checking that both sides have the same fields with matching types, so a failed bind binds nothing; `signals(name)` creates the matching signals. Neither is a `Model`: the ports and signals are ordinary ones that register as always, and a struct only refers to them, with the type erased (`StructFieldType` + pointer, and for a port field a table of functions, `PortStruct::Ops`, filled in by the typed `add()` overloads). `StructFieldType` compares types by name and must be used for every comparison of field types: a model's extension module and `_framework` each link `dspsim-core` and have their own `std::type_info` of a type, and with libc++ on macOS those do not compare equal (`std::type_index` passed on Linux and Windows and failed on macOS; only a model in its own extension module shows it, which the macOS CI jobs run). A struct port is a class derived from `PortStruct` whose ports are members, added in the constructor. **`PortStructArray`** / **`SignalStructArray`** are arrays of structs (`detail::NdView<PortStruct>` / `NdView<SignalStruct>`, so indexing and slicing are those of the other arrays; `NdView`/`NdArray::read()`/`write()` are templates so that an element type without a value compiles): an array of structs is NOT presented as a struct of arrays, the two are different constructs. `PortStructArray` refers to structs that something else owns (`PortStructArrayOf<S>` is the owning array; a `SignalStructArray` shares its structs with its copies and views), binds element by element after checking shapes and every element, and is a field kind of `PortStruct` (`SignalStructArray` of `SignalStruct`). The by-field access to an array (`input_array<T>(field)`, `array<T>(field)`, `nested(field)`; a field name in Python) returns a view over the same ports or signals (`detail::struct_field_elements()`), not a second set of them. See `docs/VerilatedPorts.md`.
- **`Module`** + **`ModuleName`**: `ModuleName` is an RAII temporary that pushes the module name onto the context's active-module stack and pops it after the member-initializer list runs, so submodules/ports declared as members get hierarchical names. Subclasses take `ModuleName` **by value** (see `DSPSIM_MODULE` / `DSPSIM_CTOR` macros in `module.h`). Copies share one construction scope that ends when the last copy dies, so a module derived from another module passes its `ModuleName` on by value. Python has no RAII: `Module.__init_subclass__` wraps each `__init__`, and the outermost call opens the scope (`with ModuleName(name)`), initializes the C++ `Module` once, runs the `__init__` chain, then calls `context._own_object()`. Python subclass `__init__` must take a `name` argument; `super().__init__(name)` is optional.
- **`Channel`** (`channel.h`): base class for user state that commits in the update phase (`request_update()` in a process, `update()` called once after the signals have committed; SystemC's `sc_prim_channel`). It shares the context's post-update stack with the derived signals (`detail::Updatable`), so it costs nothing in a design that has none. `update()` may change the channel's own state and notify events; it must not write to a signal or request the update of a channel. The same holds for an override of `SignalBase::update()` (only `Clock` and `DerivedSignal` derive from `Signal<T>`). Writes belong to the evaluation phase; this is a documented rule that the engine does not check, because a check would sit in `Signal::write()`. Python subclasses `Channel` too (see "Python bindings").
- **Bit slicing/packing** (`bits.h`, `bitsel.h`, `derived_signal.h`): `sig[{hi, lo}]` / `pack(a, b)` give an untyped, unsigned `BitSel` that can be read/written directly or bound to any integral `Input`/`Output` of the same width. Binding creates a context-owned `DerivedSignal<T>` that sources update in the same delta cycle (a second pass in `Context::update_signals()`); output writes go through to the sources. See `docs/BitSlicing.md`.
- **Processes** (`process.h`, `coro.h`): modules register processes with static sensitivity (`always(...)`) and dynamic sensitivity (`next_trigger(...)`), or C++20 coroutines (`Task<>`) that `co_await wait(...)` on time deltas, sensitivity events, or events with a timeout (`wait(event, timeout)` returns a `WaitResult`). A dynamic wait is the only thing a suspended coroutine waits for: static sensitivity is paused and the losing side of event-or-timeout is dismissed (time events are tagged with the process's `wake_count`). Only the scheduler resumes a process (`ProcessBase::resume()` is private; `Context` and `SensitivityEvent` are friends). A coroutine process that completes unschedules itself (`ProcessBase::unschedule()`: static and dynamic events, pending time waits), and misuse that could reschedule it throws `std::logic_error`: `next_trigger(...)` in a coroutine process, `initialize(true)` on a completed one. `Context::spawn(task)` starts a task that the context destroys when it completes (no handle; a per-transaction task would otherwise accumulate), while every other process lives as long as the context. `wait(0)` / `next_trigger(0)` end in the next delta cycle, as in SystemC. `ProcessBase::disable()`/`enable()` switch a method process off and on; a coroutine can only be disabled while it waits on its static sensitivity (otherwise `std::logic_error`). `Task<T>` coroutines are composable (`co_await` one from another coroutine of the same process; leaf waits record the process's resume point), which is how modules expose async operations such as `AxisRx::receive(n, timeout)` / `AxisTx::send(data, timeout)`. From non-coroutine code, `Context::run_until(task, timeout)` runs the simulation until the task completes and returns its value (`TimeoutError` on timeout); `run_until(event, timeout)` for a plain event. See `docs/Coro.md`. The old `SensitivityList`/`always << x` mechanism is retired (`.archive/`).
- **`vmodule/`**: wraps a Verilator-generated class as a `dspsim::Module`, with optional VCD/FST tracing. `vport.h` has one port class per way Verilator stores a port, each derived from the ordinary port or port array with a `sync()` that copies to or from the model: `VInput`/`VOutput` (one integer up to 64 bits, or `double`), `VInputArray`/`VOutputArray` (unpacked arrays, `VlUnpacked`), `VInputWide`/`VOutputWide` (more than 64 bits, `VlWide`: an array of 32-bit words, least significant first, as the last dimension; the top word has the remaining bits and inputs are truncated to them), `VInputBits`/`VOutputBits` and `VInputWideBits`/`VOutputWideBits` (a field of a packed struct: a range of bits of one port, written without touching the other fields). The constructors take the verilated port itself and deduce shape and storage from its type. A struct port is a generated `PortStruct` subclass with one of these per field (`verilator_struct.jinja`; `tests/cpp/StructModel.h` and `StructArrayModel.h` are the hand-written equivalents): an unpacked struct is a C++ struct in the verilated model with a member `__PVT__<field>` per field (`Port.vl_member`, a Verilator internal like `m_storage`), a packed struct is one vector with the first field in the top bits. An array of structs is a `PortStructArrayOf` of the same generated class: each element is constructed by `detail::vl_structs<S>()` from one verilated struct (`vl_element_pointers()`), or from a pointer to the first word of one packed vector (`vl_word_pointers()`; the bits ports have a constructor that takes the word pointer, which overload resolution prefers when the struct class passes its `struct_ext` on). `Port.shape` of a struct port is the shape of the array; `Port.vfield_type()` / `vfield_args()` / `vport_args` in `module_info.py` decide the C++ type and constructor arguments of every case, and `tests/test_verilator_json.py` pins them. A packed union and a packed array (also of structs) are the vector of their bits: the members of a union overlap, so separate input ports would overwrite each other. Unpacked unions are not supported (`ValueError` when the module is loaded). `docs/VerilatedPorts.md` has the mapping from SystemVerilog ports.
- Hot path (the run loop) is performance-critical; elaboration-time code should favor a clean interface instead. The engine is memory-bound (a deep DFF chain costs ~7 L1 misses per process evaluation), so layout matters: `SignalBase` keeps the fields that `write()`/`update()` touch last, next to `Signal<T>::d_/q_`; `ProcessBase` keeps its per-evaluation flags first; `SensitivityEvent` allocates its subscriber lists lazily so an unsubscribed event (most of them) is 24 bytes and costs the signal that notifies it an inline null check (`notify_committed()`); `FlaggedStack::push_back()` must stay inlined, which is why its growth path `grow()` is noinline (`PlainStack`, the list of notified events, is the same without the flag); inlining on the run cycle is pinned with `DSPSIM_FLATTEN` (`Context::eval()`: the update phase and `SensitivityEvent::trigger()` are part of the scheduler's loop) and `DSPSIM_NOINLINE` (the rare paths: stack growth, `dynamic_event_triggered()`), from `utils/inlining.h`, because the unity build otherwise inlines by size and an unrelated edit moves the benchmarks by 5 to 12%; `ProcessBase`'s flags are plain `bool`s (bit fields made time waits 10% slower); the subscriber lists of an event are one cache line that holds the first subscribers inline (`SensitivityEvent::Subscribers` in `event.cpp`), because the path from an event to the process it wakes is a chain of dependent loads; coroutine frames come from a per-thread pool (`TaskPromiseBase::operator new`); `DSPSIM_METHOD` binds the member function at compile time (`register_method<&M::eval>(this)`, a `MethodProcess` with a plain function pointer, no `std::function`). The leaf awaitables that `wait()` returns by value (`Wait`, `WaitTimeEvent`) are a single pointer: an awaitable of 16 bytes or less must not have a member narrower than a register, or every `co_await` stalls on a failed store-to-load forward (see `WaitBase` in `coro.h`). The `chain/dff/n=500` benchmarks are the reference for this path (`uv run scripts/benchmarks.py --configure chain/dff/n=500`).
- **Pre-release: no compatibility constraints.** dspsim has not been officially released and has no downstream users. Prefer the cleanest interface over keeping an existing one: rename, remove or change C++ and Python APIs freely, with no deprecation aliases or compatibility shims. Once there is an official release, API/ABI stability becomes a consideration and this note should be replaced.
- **Performance target**: the benchmarks compare against SystemC, and being comparable to SystemC is good enough. When a benchmark is on par with or faster than SystemC, stop optimizing; only a clear regression against SystemC (or against `main`, measured with the same binary args on both) needs work.

### Python bindings
- `src/_framework.cpp` defines the module. The bindings are split into groups that compile in parallel: `_framework.cpp` calls one `bindings::register_<group>()` per group in dependency order (base classes first), each declared in `src/include/bindings/framework.h` and defined in `src/bindings/<group>.cpp` (`engine`, `signals`, `signal_arrays`, `ports`, `input_arrays`, `output_arrays`, `structs`, `modules`), and those call the `bindings::bind_*` helpers from `src/include/bindings/*.h`. Templates are instantiated per type with suffixed names: `SignalU8..U64`, `SignalS8..S64`, `SignalFloat`, `SignalArray*`, `Input*/Output*`, `Dff*`, etc. Adding a type/class means updating both the binding header and the registration in its group file under `src/bindings/` (a new group file also goes in the top-level `CMakeLists.txt`, `framework.h` and `_framework.cpp`), and usually the re-export list in `src/dspsim/framework.py`. A binding header must include what it uses: each group only includes the binding headers it needs.
- `src/dspsim/framework.py` is the public Python API: re-exports `_framework` and subclasses `Context`/`Module`. The Python `Context` relies on the C++ construction lock; the `create` bindings release the GIL while waiting (GIL handling stays in the bindings, never in `dspsim-core`). Also adds Python-side async tasks via `add_task`, `await self.wait(...)`, backed by `PyTask`; `ctx.run_until(awaitable, timeout)` drives any awaitable to completion. C++ `Task<T>` methods are exposed to Python by wrapping them with `py_task(context, task)` in the binding, plus one `bind_task<T>` registration per result type (`Task`, `TaskBool`, `TaskList*`); `AxisRx*`/`AxisTx*` (`axis_bindings.h`) are the examples. `py_task()`, `PyTaskAwaitable<T>`, `bind_task<T>()` and `bind_task_once<T>()` are in `src/include/dspsim/bindings/task.h`: `src/include/dspsim/bindings/` holds the binding helpers that are installed with the dspsim headers (add them to the `FILE_SET`), because the extension modules of models use them too, while `src/include/bindings/` is the framework's own and is not installed. An installed binding header includes nanobind and what it uses, never `nb_include.h`. `PyTaskAwaitable<T>` is one C++ type whatever module instantiates it, and nanobind finds its Python class by C++ type across the `dspsim` domain: a model extension returns the framework's `TaskBool` for a `Task<bool>` and must not bind it again; for other result types it calls `bind_task_once<T>()`, which binds only if no loaded module has.
- `SignalStruct`, `PortStruct` and the arrays `SignalStructArray`, `PortStructArray` (`struct_bindings.h`) are bound once, for every struct: a field is an attribute (`__getattr__`) and an item, and the binding finds the Python class of a field by comparing its `type_index` with the fixed list of value types (`StructFieldTypes`), which must match the types that the other groups bind. A port field is returned as a reference that keeps the struct alive (and through it the module); a signal field that the struct owns is returned as its `shared_ptr`. Python code builds structs with `add()`: a `SignalStruct` then holds a reference to the signal (nanobind's `shared_ptr` caster), a `PortStruct` keeps the port alive with `keep_alive`. A verilated module returns its struct ports as `PortStruct &` (`PortStructArray &` for an array), so model extensions bind nothing per struct. An array is indexed like the other arrays (`resolve_key()`); a string key or attribute gives one field of every element as a view (`InputArrayView*`, `SignalArrayView*`, or a struct array of the nested structs) that keeps the array alive. **Keep-alive cycles**: nanobind's keep-alive edges are invisible to Python's garbage collector, so a cycle of them is never released (nanobind reports "leaked instances" at exit). Python-built structs hold their ports (`keep_alive`), so nothing that is returned from a struct or a view of one may be made to keep that struct or view alive if it is an existing Python-owned object: return elements with `rv_policy::reference_internal` (which adds the edge only for a new wrapper), not with a `nb::keep_alive<0, 1>()` policy (which always adds it). `bind_ndarray_common()`'s `__getitem__` does this; `tests/test_struct.py::test_struct_array_views_are_released` checks it in a subprocess.
- `framework.py` also has the Python-only helpers for ports wider than 64 bits: `to_words()` / `from_words()` between an integer and 32-bit words, and `signal()` returns a `SignalArrayU32` for a width over 64.
- A Python class derives from `Channel` and implements `update()` (`channel_bindings.h`: `PyChannel` is a nanobind trampoline, and `ChannelAccess` exposes the protected `request_update()`). Python code can also create an event, `SensitivityEvent(context)`, and `notify()` it. The context refers to both by raw pointer (a channel on the update stack, an event in the processes subscribed to it), so the bindings hand them to the context, which keeps them alive until it is cleared (`Context::own_object(std::shared_ptr<void>)`, the one way the context shares ownership of anything: `Model::create()` and `SignalArray::create()` use it as well). An object that C++ allocates is passed as its `shared_ptr`. An object that Python constructs (a `Module` or `Channel` subclass) has its C++ part inside the Python object, so the context holds a Python reference instead: `python_reference()` (`python_reference.h`) makes a `shared_ptr` whose deleter drops the reference, and `Context._own_object()` is that for Python code. Anything else that Python creates and the engine keeps a pointer to needs the same.
- Stubs (`_framework.pyi`) are generated at install time by `dspsim_add_stub`, which takes optional nanobind stubgen pattern files as extra arguments. `src/_framework.pat` rewrites the array `__getitem__` overloads (element vs. view), whose overlap is intended and needs a `# type: ignore` that `nb::sig` cannot emit; when those signatures change in `bind_ndarray_common()` (`ndarray_bindings.h`) or an array class family is added, update the pattern in the same change and re-check the stub. pyright skips files under `.venv`, so to check the stub, copy it elsewhere first: `cp .venv/lib/python3.14/site-packages/dspsim/_framework.pyi /tmp/ && uv run --with pyright pyright /tmp/_framework.pyi`.
- All extensions use `NB_DOMAIN dspsim`, and separately built model extensions must call `dspsim.link_module(module)` to share the main global `ContextFactory`, or their models register with a different context.

### Verilator codegen (two paths, same Jinja templates in `src/dspsim/templates/`)
1. **Library build (CMake)**: `dspsim_add_module()` in `cmake/dspsim-utils.cmake` runs `python -m dspsim.generate --pyproject ... --output-dir ...`, which reads `[tool.dspsim]` from a pyproject (`project.py`: sources, include_dirs, parameters, trace), introspects each module with `verilator --json-only` (`verilator.py`, `module_info.py`: a `Port` has width, sign and unpacked shape, `is_wide` above 64 bits, and for a struct port the `Port`s of its fields with `packed` and `lsb`; `_parse_port()` follows typedefs, enumerations, packed arrays and structs), and emits nanobind wrapper C++ + a CMake include that verilates the sources. See `examples/some_example/`. Downstream projects find the installed package via `dspsim --cmake_dir` / `dspsim --include_dir`. C++ modules are in `[tool.dspsim.cpp]` (`CppProjectConfig` in `project.py`): what they are built with is library-wide (`include_dirs`, `sources`, `definitions`, `packages`, `libraries`, one `bindings` header, `strict`) because they share the extension module's target, and each `[tool.dspsim.cpp.models.<Name>]` has `header`, `cls`, `parameters`, `methods`. They go through the same `CppHeader.module_info()` and `cpp_module_bind.h.jinja` as the JIT builder; the generated include adds the sources, definitions and libraries to the target and lists the parsed files as `CMAKE_CONFIGURE_DEPENDS`, since generation happens at configure time. Relative paths in the pyproject are relative to its directory. The library path has two tests: `tests/test_library.py` configures and builds a mixed library with CMake against the installed dspsim, and `examples/some_example` is the full scikit-build-core package (`cd examples/some_example && uv sync --refresh-package dspsim && uv run pytest`; `--refresh-package` because uv caches the dspsim wheel it builds for a path dependency by the cache keys in `pyproject.toml`, which do not include the Python sources, the templates or `cmake/`). The model libraries of a library build are compiled with `POSITION_INDEPENDENT_CODE` (set in `verilate_include.cmake.jinja`), and the extension with `NOMINSIZE`. `render_template()` is in `dspsim/templates/__init__.py` and the pieces that the generator and the JIT builder share (`cmake_executable()`, `toolchain()`, `dependency_compile_args()`, `build_key()`) in `toolchain.py`: neither imports the framework.
2. **JIT build (Python)**: `dspsim.builder.vbuilder(source)` class decorator / `build_vmodule()` generates a per-model CMake project, builds it under `.dspsim_cache/` (override with `DSPSIM_CACHE_DIR`), then imports it and calls `link_module`. Class annotations override parameters and optionally validate ports. `verilator_args` (also `[tool.dspsim] verilator_args` and per model in a library) are extra Verilator arguments, kept in `ModuleInfo.verilator_args`: `load_model_info()` passes them when it reads the module, the CMake templates append them to `VERILATOR_ARGS` (quoted with the `cmake_quote` filter), and they are in the build key with the rest of the `ModuleInfo`. **Build names** (both JIT builders): a build is `<PythonName>_<key>`, where `_build_key()` hashes the description of the module (name, parameters, ports, options, include directories) and the contents of every source file (for Verilog, the files Verilator read: `ModuleInfo.source_files`; for C++, the header and its non-system includes: `CppHeader.source_files()`). The cache directory, the extension module (`_<PythonName>_<key>`) and the generated C++ class are named after it, while the Python class keeps its name (`ModuleInfo.python_name`, `CppModuleInfo.name`). So the same name with another source, an edited source or other parameters is a separate build that loads next to the first, and only an identical build is reused (`_load_built_module()` returns the imported class). What is in the key and what is not: the key has what dspsim itself can see (options and user sources), so that a different build gets a different name. Everything else a module depends on (system and third-party headers, dspsim's headers and library) is left to the build system, which has the compiler's dependency files: `_build()` therefore always runs the build step (`cmake --build`, a few milliseconds for a module that is up to date, with the real CMake executable from `_cmake()` because the `cmake` script on the path costs an interpreter start) and never skips it, and a stale module is rebuilt in place. Only the configure step is skipped, when the build directory's stamp (`__build_stamp__.txt`: the hash of the generated files and `_toolchain()`) is unchanged. A module that is rebuilt after it was imported raises `RuntimeError` in `_load_built_module()`. `CppHeader.load()` returns the header as it was parsed before in the process if its files are unchanged; in a new process the libclang parse (about 0.6 s) is what an existing C++ module costs. `tests/test_cppbuilder.py::test_cppbuilder_system_header` changes a header on `CPLUS_INCLUDE_PATH` between processes to check the rebuild. The name of the Python class is in the key on purpose: sharing one build between names would make a class report the name it was first built under. Inside a build directory, `generate_files()` still only rewrites files whose rendered content changed. Whatever a generated file depends on must be in the description or the sources, or two different builds share a name.

### VHDL models (`docs/Vhdl.md`)
A VHDL source (`.vhd`, `.vhdl`) goes through the same two paths as SystemVerilog: `load_model_info()` (`project.py`) first calls `dspsim.ghdl.transpile()`, which writes one SystemVerilog file for the entity and the given generic values, and that file is the source of the model from there on (`ModuleInfo.source`; `ModuleInfo.vhdl_files` has the VHDL files, which a library build lists as `CMAKE_CONFIGURE_DEPENDS`). Nothing after that knows about VHDL. GHDL is an external program (`DSPSIM_GHDL`, or `ghdl` on the path; versions 5 and 6), needed only to build, and the only VHDL tool: dspsim does not simulate VHDL, and synthesizable VHDL is the scope.
- `transpile()` runs `ghdl -i`/`-m`, then `ghdl -r <entity> -g... --dump-rti --disp-tree=port --stop-time=0ns` to get the generics and ports with their elaborated types (`parse_rti()`; `--dump-rti` is a debugging output, not a documented interface, and the only source of elaborated types that needs nothing but the executable: pyGHDL has no wheels for Python 3.14), then `ghdl synth --out=verilog`. It elaborates once without generics, to learn their types, and again with them.
- The netlist has lost the interface: generics are constants, every port an unsigned vector, a record port one port per element (`\port[element] ` in GHDL 6, `port_element` in GHDL 5), arrays and nested records one flat vector. `wrapper()` (template `vhdl_wrapper.sv.jinja`) writes the module named after the entity around it: generics as parameters, ports with their types (`signed`, unpacked arrays, unpacked structs for records in a package `<Entity>_pkg`), and concatenations between the two. **Packing order** (`_leaves()`): record elements from the least significant bit in declaration order, array elements from the most significant bit left to right; a dspsim array index is the position from the lowest VHDL index. `wrapper()` raises if a netlist port does not have the bits that dspsim computes for its type, and `tests/test_vhdl.py::test_vhdl_model` checks every element of `hdl/vhdl/VhdlModel.vhd`, whose outputs change each element differently.
- The netlist's module is renamed `<Entity>_ghdl` (instance `impl_`), its part of the file is in `` `begin_keywords "1364-2005" `` because GHDL writes Verilog (a port can be called `int`), and the declarations of GHDL's anonymous nets (`n123`) are wrapped in `/* verilator tracing_off */`. Names that are keywords of SystemVerilog, C++ or Python get an underscore at the end (`_RESERVED`); helper names end with an underscore too (`impl_`, `flat_0_`), which no VHDL identifier does.
- Generics and ports keep the spelling of the source (`_declared_name()` reads the identifier at the `sloc` that GHDL prints, which is otherwise all lower case). Integer, boolean (a `bit` parameter: 0/1 in Python) and string generics can be set; a `real` is a read-only parameter (GHDL cannot override it), and `_generic_arguments()` skips a value that is the default, so that a library that passes every parameter back does not trip over one.
- The output is `<cache>/vhdl/<entity>_<digest>/<Entity>.sv`; the digest has the contents of the VHDL files, the generics, the options, the GHDL version and the hashes of `ghdl.py` and the template, so a change to the generator is a new directory. Options: `vhdl_sources`, `vhdl_entity`, `vhdl_std`, `ghdl_args` on `vbuilder`/`build_vmodule` (`VhdlOptions`); `vhdl_sources`, `vhdl_std`, `ghdl_args` in `[tool.dspsim]` and, with `entity`, per model. CMake: `dspsim_vhdl_source(<var> SOURCE ...)` in `cmake/dspsim-utils.cmake` runs `python -m dspsim.ghdl` at configure time (`tests/cpp/CMakeLists.txt` uses it for `test_vmodel_vhdl.cpp` when GHDL and the dspsim package are there).
- Tests: `tests/test_vhdl.py`. The ones that run GHDL are skipped without it (`needs_ghdl`); the others read a recorded dump (`RTI`) and a small netlist, so the parser and the wrapper are tested everywhere. Run them with both GHDL versions after a change to `ghdl.py`. The wheel CI has no GHDL; `.github/workflows/vhdl_tests.yml` runs these tests with a GHDL release on Ubuntu.

### C++ module JIT build (`docs/CppBuilder.md`)
`dspsim.builder.cppbuilder(header)` class decorator / `build_cppmodule()` binds a hand-written C++ `Module` from its header, through the same cache, build and import steps as `vbuilder` (templates `cpp_module_*.jinja`). `cpp_parser.py` (`CppHeader`, `load_cpp_module_info()` → `CppModuleInfo` in `module_info.py`) reads the class with libclang, an optional dependency (`dspsim[cpp]`, the `libclang` wheel; `DSPSIM_LIBCLANG` selects another library). The parser sees preprocessed code, so `DSPSIM_MODULE`/`DSPSIM_CTOR` need no special handling. Bound: the public constructors whose first argument is a `ModuleName` (`nanobind::new_(&create_module<M, Args...>)`; `create_module` in `module.h` is variadic, with `Args` given explicitly), the public port members (`.def_ro`), the public members of a class that derives from `PortStruct` or `PortStructArray` (struct ports and arrays of them: `_port_struct_class()`, a `CppPort` with `is_struct`, bound as a property that returns `PortStruct &` or `PortStructArray &`; the fields are not parsed, Python reads them from the object) and the public methods (lambdas that take `M &self`, so methods of base classes and overloads need no casts), including those of base classes. Left out silently: process bodies (found by scanning the class's tokens for `DSPSIM_METHOD`/`DSPSIM_CORO`), operators, member function templates. Left out with a `CppBindingWarning` (`strict=True`: `TypeError`), each recorded as a `CppSkipped` with a reason: anything with a type the bindings cannot convert (`_check_type()` in `cpp_parser.py` is the whitelist: values, strings, the `nanobind/stl` containers, classes and enumerations). The parser cannot know which classes have Python bindings, so the generated code tests `nanobind::type<T>().is_valid()` at import, leaves the function out and lists it in the module's `_unbound`, which the builder reports. Literal default arguments become Python defaults; for any other default the function is bound once per argument count and C++ supplies it (`CppFunction.overloads`). Class templates: the template parameters are set with class annotations like Verilog parameters (`T: type = np.int16` or `T: str = "demo::Sample"`, `SHIFT: int = 3`, `FLAG: bool`), or `build_cppmodule(parameters={...})`. The parser builds the argument list (positional, so defaults before the last parameter that is set are pasted from the declaration), then parses a second translation unit that instantiates the template (`sizeof` in the `dspsim_probe` namespace: the class, not its member functions) and reads the real member types and the resolved arguments from it. Integer and `bool` arguments are bound with `.def_ro_static` on a generated `dspsim::generated::<Name>Parameters` struct; type arguments are class attributes set with `cls.attr()` (the numpy type, or the canonical C++ name). **libclang versions**: the code is written against the libclang 18 Python bindings of the wheel, whatever library is loaded. libclang 18 does not give the members or base classes of a template instance through cursors (`Type.get_fields()` works; the bases come from `clang_getSpecializedCursorTemplate`), so with it a class template only gets its ports, template arguments and `ModuleName`-only constructor, and the rest is reported as skipped. libclang 20 has `clang_visitCXXMethods`/`clang_visitCXXBaseClasses`, which `_visit()` calls through ctypes; `_cindex()` prefers a system libclang 20+ (`_system_libraries()`) to the wheel's, and `DSPSIM_LIBCLANG` is a path or `bundled`. Tests branch on `supports_template_members()`: run `tests/test_cppbuilder.py` both ways (`DSPSIM_LIBCLANG=bundled uv run pytest tests/test_cppbuilder.py`) after changing the parser; CI only has the wheel. **Platforms**: verified with MSVC on Windows, both from a developer prompt (Ninja, VS 2022) and without one (the default Visual Studio generator and the newest Visual Studio, which is what the wheel CI has). Two things the parser does for that: on Windows it defines `_ALLOW_COMPILER_AND_STL_VERSION_MISMATCH`, because Microsoft's standard library rejects a Clang older than it was tested with; and an error diagnostic inside a system header is a `CppParseWarning`, not a `CppParseError` (`_parse()`), because a newer standard library uses builtins that libclang 18 lacks in a few type traits (VS 2026: 14 errors) while the rest parses. Errors in user files and fatal errors still raise. Do not depend on a generator: the Visual Studio generators have no `compile_commands.json` and put the extension in `build/Release/`. A class declared with `DSPSIM_MODULE` has an extent that starts in a macro expansion, for which `cursor.get_tokens()` returns nothing: use `_tokens()`. nanobind keeps one Python class per C++ class, so the bindings derive a class of the build's name from the module's class (`dspsim::generated::<PythonName>_<key>`, inheriting its constructors) and bind that as `M`; a method that takes or returns a reference to the module itself uses `M` (`_refers_to()`), and a `final` module is bound as it is (a second, different build of it in one process raises `RuntimeError`). Tests may build the same class in several tests (same key, same class); tests that write headers to `tmp_path` set `DSPSIM_CACHE_DIR` there, because the path is part of the key and every run would otherwise add builds to the project's cache. A method that returns a `dspsim::Task<T>` is bound as `py_task(self.context(), self.method(...))` after `bind_task_once<T>(m, "_Task_<T>")`; such a method must take values by value (a coroutine keeps reference parameters, and a value that Python converted is gone when the task resumes), so one that takes a reference or pointer to a value is skipped with that reason. **What a C++ module is built with** (`build_cppmodule()` keyword arguments, all in `CppModuleInfo` and so in the build key): `sources` (compiled into the extension module target; not parsed, only searched by `_process_names()` for `DSPSIM_METHOD`/`DSPSIM_CORO` registrations, each attributed to the `Class::Class(` constructor definition before it), `definitions` and `include_dirs` (passed to both the parser and CMake), `packages`/`libraries` (`find_package`/`target_link_libraries`; their include directories and definitions are only known to CMake, so `dependency_compile_args()` in `toolchain.py` configures `cpp_dependencies_cmake.cmake.jinja` once per set under `dependencies_<hash>`, which writes them with `file(GENERATE)` from the properties of a target that links them; not from `compile_commands.json`, which the Visual Studio generators do not write), and `bindings`, a user header that defines `template <typename M> void dspsim_bind(nanobind::module_ &, nanobind::class_<M, dspsim::Module> &)`, called right after the class is created and before the generated constructors and methods, so that classes it binds pass their import-time `is_valid()` guards. The module target is created with `NOMINSIZE`: nanobind otherwise appends `-Os` to an extension, after `-O3`, and the model's code is compiled in that target. `_import_built_module()` registers the extension in `sys.modules` under its build name. `tests/test_cppbuilder.py` uses the headers in `tests/cpp_modules/`. `dspsim.include_dir()`/`cmake_dir()` point at where `_framework` is installed, which is not the source tree in an editable install. The CMake package config finds Verilator optionally, so a C++ module builds without it.

## Conventions (from docs/StyleGuide.md)

- C++: Allman braces, 4-space indent, braces required even on one-line bodies. PascalCase classes, snake_case functions/variables, private member variables with a trailing underscore (`name_`). No C++ identifier starts with an underscore; private methods have plain names. Python bindings use a leading underscore for private names.
- Class member order: types, constants, ctors/dtor, static factories, public, protected, private methods, then public, protected, private data. Members must be declared in initialization order (`-Werror=reorder` is on). A `Context*` member goes first.
- Prefer forward declarations over including headers of classes that reference each other. Put definitions in `.cpp` files, not inline in headers. Definitions follow declaration order.
- **Header weight**: a header includes only what its own declarations need (`signal.h`/`port.h` do not include `context.h`; `module.h` deliberately includes `context.h`, `process.h`, `coro.h` because every module uses `DSPSIM_METHOD`/`DSPSIM_CORO`/`wait()`). Keep `<thread>`, `<mutex>`, `<condition_variable>`, `<format>`, `<filesystem>`, `<ranges>` and spdlog out of public headers: hide such members behind a struct defined in the `.cpp` (`ContextFactory::State`, `SensitivityEvent::Subscribers`).
- **What stays inline**: the one-line accessors on the run cycle, each with a comment. (1) What model code calls on every evaluation, since model code is compiled outside the core: `Signal::read()`, `Input::read()`, `Output::write()`, `pos()`/`neg()`/`change()`, `Model::context()`, `Module::inputs()`/`outputs()`, `Module::wait()`, the awaitables' `await_ready()`/`await_resume()`, `Task`. (2) What the scheduler reads on every evaluation: the `ProcessBase` flags and counters, `TimeEvent` accessors and comparisons, `Context::current_process()`/`update_count()`, the `scheduled_flag()` functions, `SignalBase::width()`, `BitPart::width()`. Templates over a fixed type list (`Signal<T>`, `Input<T>`, `Output<T>`, `DerivedSignal<T>`) are defined and explicitly instantiated in the `.cpp`. See "Headers and inline code" in `docs/Architecture.md`.
- **Core build configuration** (`src/CMakeLists.txt`, explained in "Build configuration of the core library" in `docs/Architecture.md`): `dspsim-core` is a unity build (`DSPSIM_UNITY_BUILD`, default ON) with **no LTO**, because the static library is installed into the wheel and LTO objects only link with the same compiler version that built them. `-fno-semantic-interposition` is `PUBLIC` on GCC/Clang for ELF targets: without it GCC does not inline exported functions inside the Python extensions (shared libraries). `-fno-stack-protector` is set on the core. Consequences: file-local names must be unique across the core `.cpp` files; `-DDSPSIM_UNITY_BUILD=OFF` gives per-file compiles for working on the core (faster one-file rebuilds, slower simulation, do not benchmark it); `-DCMAKE_INTERPROCEDURAL_OPTIMIZATION=ON` gives whole-program LTO for local C++ executables (faster than the default for the benchmarks, never for wheels). `CMAKE_CXX_SCAN_FOR_MODULES` is OFF (no C++ modules; the scan is an extra preprocessor run per file), also in the generated model projects.
- **Logging**: only `src/log.cpp` includes spdlog (header-only on purpose: the compiled spdlog library caused distribution problems; 7-10 s per including file) and it is excluded from the unity batch. Core code logs with the `DSPSIM_LOG_*` macros from the internal header `src/log.h` (`DSPSIM_LOG_ERROR(context()->logger_, "Port " + hier_name() + " is not bound")`); the message expression is only evaluated when the level is enabled, and `TRACE`/`DEBUG` are compiled out by `DSPSIM_LOG_ACTIVE_LEVEL`. Build messages by concatenation, not `std::format` (about 2 s of compile time per file that uses it).
- **Measuring performance**: use `scripts/benchmarks.py`. Instructions per iteration are exact and repeatable: to see what a change does to dspsim, `--save` a baseline, make the change, `--compare`. Cycles per iteration are the time, and the only number that compares dspsim with SystemC (the engines differ in instructions per cycle). They depend on the memory layout (where the design's objects land relative to cache lines and each other): 2 to 8%, over 10% in single cases, identical in every launch of the same command and different for the next build or command line. So the driver runs every repetition with a different layout (`--layout`), reports the median and the spread, and a difference inside the spread is noise: do not read a cycle change of a few percent between two builds as an effect of the code unless the instructions moved too. The C++ benchmarks are executables and the Python extensions are shared libraries, and the same source can compile differently for the two, so also check a hot-path or build change on a simulation driven from Python (`perf stat -e instructions:u`).
- Doxygen docstrings on header declarations. Add tests for new features.
- `dspsim-core` builds with `-Wall -Wextra -Wpedantic -Werror`. New public headers must be added to the `FILE_SET HEADERS` list in `src/CMakeLists.txt`, and new sources to `add_library(dspsim-core ...)`.
- **Access**: each core class has a user API (`public`), an extension API (`protected`: what a new process type, leaf awaitable, port or model needs) and engine internals (`private`). Engine classes reach each other through `friend` declarations, each with a comment saying why. Code outside `dspsim-core` (the bindings) uses `detail::EngineAccess` (`detail/engine_access.h`) and never gets its own friend declaration. Tests assert on observable behavior; for invariants with no observable effect (cleanup, "did not run") they use the read-only `testing::EngineInspector` in `tests/cpp/engine_inspector.h`. spdlog stays internal: `Context::logger_` is private, and tests and models log with `ctx->log(level, msg)`. See "Public interface and access" in `docs/Architecture.md`.
- **Python private names**: bindings that are not user API get a leading underscore (`_own_object`, `_get_global_context_factory`); stubs are generated with `INCLUDE_PRIVATE` so they stay typed. `framework.py`'s `__all__` is the public list.
- **C++ tests**: all `tests/cpp/*.cpp` link into one binary, so wrap file-local helper classes in an anonymous `namespace { }` to avoid silent ODR violations. New test files must be added to `tests/cpp/CMakeLists.txt`. A Catch2 listener (`test_listeners.cpp`) resets the global context after each test case. Verilated test models (`hdl/Skid.sv`, `NDArrayModel.sv`, `WideModel.sv`, `StructModel.sv`, `StructArrayModel.sv`) are built there with `verilate(...)`, all into the one `test_models` library: `verilate()` adds Verilator's runtime sources to its target, so one target compiles the runtime once (the models in a target must share a trace format). `sc_time_stamp()` is defined once for that library, in `tests/cpp/sc_time_stamp.cpp`: Verilator's runtime needs it, it is a weak symbol with GCC/Clang, and MSVC rejects a second definition in the same program.
- Python is formatted with ruff (preview format enabled).
